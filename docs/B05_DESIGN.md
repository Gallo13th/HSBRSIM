# B05 设计：优化器强度（唯一因子 = 每 300M 决策的策略位移）

> 结论性前提（2026-11-06 实测）：B01→B03 用了 **300M 决策**，模型权重只挪了 **1.54%**；
> `approx_kl/iter` 一直是 0.0004–0.004，而 `target-kl` 上限是 **0.02** —— 相当于闸门只开了 1/20。
> B04（2 席冻结克隆）在 150M 的 384 局是 **2.003 / win 39.8%**，而 B03@150M 是 **1.784 / 47.9%**，
> 判为无效并**已停止**（详见 B04_DESIGN §6）。B05 因此改攻优化器强度，其余配方与 B03 逐字一致。

## 1. 位移模型（实测校准）

```
Δθ_rel ≈ 0.45 × lr_avg × (优化器步数 / iter) × iters
        （0.45 = Adam 有效步长/名义 lr 的校准系数，由 B01→B03 的 1.54% 反解）
```

| 配方 | lr_avg | 步/iter | iters | 线性预测 | **实测** |
|---|---:|---:|---:|---:|---:|
| B03（现状） | 8.8e-7 | 9 | 4285 | 1.5% | **1.54%** ✓（晚期 0.016%/10M） |
| **B05（本配方）** | 2.25e-6 | 33 | 4285 | 14.3% | **见下表（非线性）** |

**⚠️ 预测偏差（2026-11-06 实测修正）**：位移不是线性增长，Adam 的步长方向相关性有限 ⇒ 近似 `sqrt(steps)`。
实测 B05（相对 B03 起点）：

| 决策 | 10M | 20M | 30M | 40M | 50M |
|---|---:|---:|---:|---:|---:|
| 相对位移 | 0.48% | 0.58% | 0.66% | 0.80% | **0.86%** |
| 每 10M 增量 | — | +0.10 | +0.08 | +0.14 | +0.06 |

- 早期速率是 B03 的 **~30×**（B03 晚期 0.016%/10M），但总量按 sqrt/近线性外推 **300M ≈ 2–3.5%**（不是 14%）。
- **判据随之修正**：不再要求"50M 位移 ≥1.5%"，改为**每 10M 增量 ≥0.05%**（当前 0.06–0.14，达标）。
- 真正的判据只有行为指标（150M/250M/300M 的 384/768 局面板）；位移只用来确认"闸门开着"。

## 2. 配方（唯一因子：优化器强度三件套）

| 参数 | B03 | **B05** | 理由 |
|---|---|---|---|
| `--lr` | 1.17e-6 | **3.0e-6** | 每步位移 ×2.6 |
| `--lr-min-ratio` | 0.5 | 0.5 | 保留线性退火 |
| `--minibatch` | 2048 | **1024** | 步数 ×2 |
| `--grad-accum` | 4 | **2** | 步数 ×2（有效批 8192→2048） |
| `--epochs` | 1 | 1 | 靠更多小步，不做多遍重复 |
| `--max-updates` | 4500 | **4300** | lr 按 iter 退火，匹配 300M 的 ~4285 iter |
| `--target-kl` | 0.02 | 0.02 | 安全阀：单 minibatch KL>0.03 跳过并结束 epoch |
| `--clip` / `--max-grad-norm` | 0.2 / 1.0 | 同 | |
| `--entropy-coef` | 0.001 | 同 | 单变量，先不动 |
| 对手 / 课程 | bots + 3 席 human p0.90 | **同 B03**（`FROZEN_SEATS=0`） | 隔离变量 |
| 起点 | — | **B03 300M 权重 + 真 fresh optimizer** | B04 权重更差 |
| 预算 | 300M | 300M | 预计 ~10–13h |

## 3. Pilot 判据（前 10M 必须达标才放行）

| 检查 | 目标 | 实测（前 12 iter） |
|---|---|---|
| `approx_kl/iter` | 0.002–0.010 | **0.0067 / 0.0076** ✓ |
| `clip_frac` | 0.02–0.15 | **0.065 / 0.069** ✓ |
| `policy_loss` | 明显大于 B03 的 0.0005 | **0.0035 / 0.0038** ✓ |
| `entropy` | 0.70–0.80，不塌 | 0.717–0.731（待观察） |
| 权重位移 | ≥0.5%/10M | 10M 时用 checkpoint 直接量 |
| 吞吐 | ≥6k dec/s | ~8.3k dec/s ✓ |

不达标处置：`lr 3e-6 → 2e-6`（保守档 ~7% 位移）；entropy 塌 → `entropy-coef 0.003`；KL 连续 >0.015 → 降 lr。

## 4. 判据与早停

- 150M：384 局 vs **B03@150M（1.784 / 47.9% / 长强 18.2%, n=22）**；同时权重位移应 ≥5%
- 300M：384 + 768 局 vs B03 300M（768 局 1.810 / 45.3%）
- **早停**：150M 时位移 <3%（说明还有别的抑制）或 384 局 ≥1.88（比 B03 差 0.1+）→ 停并回退

## 5. 这个实验能区分什么

- 位移到 ~14% 仍无改善 ⇒ 瓶颈是**信号结构**（终局 rank utility + `--sims 0` 无搜索），下一步必须上
  `--behavior-mix-eps`（MCTS 生成优于策略的目标）或 6k+ MMR 人类 BC
- 位移到位且指标改善 ⇒ B01/B03/B04 的"无效"应重新解释为**预算不足以产生行为变化**

## 6. 顺带修复的两个脚本回归（2026-11-06 发现）

1. `train_block_clean.sh` 的 `--lr/--max-updates` 被写死（1.17e-6 / 3000），忽略 `run_stage300m.sh`
   传的 `LR`/`MAX_UPDATES` ⇒ **B04 实际用 max_updates=3000**（比 B03 的 4500 更早触底，150M 时 lr 低约 20%，
   是 B04 结论的一个次要 confound）。现已改为环境变量驱动（默认值等于原硬编码，未设时命令行逐字不变）。
2. `TS="${TS:-runs/az_entity_s61/trainer.pt}"` 的 `:-` 语义让 **TS="" 也回落到 s61 的 trainer state**
   ⇒ B04 实际不是 fresh optimizer（`loaded updates=285`）。现改为 `${TS-...}` 并给 `[ -f "$TS" ]` 校验加空值保护，
   B05 已验证 `[resume] start_iter=0 updates=0`。

### 2026-11-06 10:59 崩溃（collector 空 mask，非本配方引入）

- **现象**：`iter 752 / 56.69M` 时 `RuntimeError: worker7 采集失败: ValueError('存在无合法动作的行（mask 全 False）：rows=[4]')`，
  栈底在 `batch_eval._act_batched`（策略前向时某一行 legal mask 全 False）→ trainer rc=1。
- **性质**：**引擎级潜在 bug**（某个游戏状态没有任何合法动作，但局没结束）。B02 在 92.12M 也撞过同类错误，
  与 B05 的 lr/配方无关；B05 只是把策略打得更开，更容易走到那个罕见状态。`docs/RUST_COLLECTOR.md` 记载
  空 mask 在 Rust 采集器里是显式 `ValueError`，没有 fallback。
- **恢复**：11:14:33 从 `snapshots/step_000701`（cum **52,805,615**）续训：
  `STOP=247,194,385`、`EVAL_FIRST=7,194,385`（下一个 60M 点）、`RAMP_START=52,805,615`、`seed 27704`；
  lr 从 2.75e-6 继续（`loaded updates=701`）。损失 3.88M（1.3%）。
- **监视器**：`--dev-offset 52805615` + `relabel_b05.sh`；已知偏差同 B04（history 含崩溃前行，`cum` 高估 3.88M）。
- **待办（不阻塞当前 run）**：① 在 `collect_ppo_lockstep` 里对空 mask 加 **dump state_json + 丢弃该局** 的兜底
  （把 run-killer 变成可复现样本）；② 加 **崩溃自动重启 supervisor**（按快照自动算 DONE/STOP/EVAL_FIRST/RAMP_START），
  把每次崩溃的代价从 ≤30 分钟压到 ~5 分钟。
